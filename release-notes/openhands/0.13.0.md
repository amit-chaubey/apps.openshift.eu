# openhands 0.13.0

Released 2026-10-27.

## Changes

### Agent Canvas 1.34.0, pinned by digest

The image is built from `ghcr.io/openhands/agent-canvas:1.34.0`, pinned to the
image index digest
`sha256:638c5e3ce76df74344bb18bd85f44af395337ade8e71f04532099fb380febadf`
(new value `image.digest`). Agent Canvas 1.34.0 keeps agent-server 1.58.1, so the
settings, profile and MCP API the chart seeds is unchanged; automation moves to
1.26.0. Changes that reach this chart:

- The automation KV secret is pinned once in `~/.openhands/agent-canvas/automation-kv-secret.txt`
  on the data volume, so a rotated session API key no longer makes automation state
  unreadable.
- The static server gets the session API key through its environment instead of its
  command line.
- Upstream adds a **Settings > Runtime** page for a Docker runtime per conversation. The
  pod has no Docker daemon; conversations keep running in the pod.

The MCP icon patch (2 and 1 changes, 19 bundles renamed) and the Claude Code usage
patch (7 changes, adapter 0.63.0) apply to the 1.34.0 frontend and adapter unchanged.

### The image tag names the upstream and chart version

The built image is tagged `<image.tag>-<chart version>`, here `1.34.0-0.13.0`,
instead of the upstream version and a hash of some build inputs. The hash left out
the patch scripts, so 0.12.0 changed the MCP icon patch without a new tag and the
running image never got the change. Every chart release now builds its own image
once. A release that changes `build.tools` or `build.toolsImage` raises the new
value `build.revision`, which is appended as `-<revision>`. The BuildConfig and its
build context ConfigMap are named after the tag.

### The pod keeps the running image until the new one is built

Under Argo CD, the ImageStream, the build context and the BuildConfig sync in wave
-2, a Sync hook Job `<release>-<tag>-wait` waits in wave -1 until the build of the
new tag is Complete, and the StatefulSet follows in wave 0. Until then the pod keeps
running the previous image. A failed build fails the sync and leaves the
StatefulSet as it was; the failed Job stays until the next sync for its log. The new
values `build.wait.enabled` and `build.wait.timeoutSeconds` (default 3600) control
the hook. Plain `helm upgrade` does not wait.

## Upgrade

The first sync creates the BuildConfig `<release>-1-34-0-0-13-0` and waits for its
build, about as long as a build took before; the agent stays available meanwhile.
The pod then restarts once on the new image. An Application with `prune: true`
removes the BuildConfig and ConfigMap of the old hash tag. A browser loads the new
frontend on its next page load. Nothing else to do.
